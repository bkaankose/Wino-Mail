A product design language for Wino Mail

Calm, personal, and fast—without making mail feel generic.

This guide turns Windows and Fluent principles into decisions for Wino’s mail, calendar, contacts, intelligence, onboarding, and settings experiences. It is the starting point for new features, not a retrospective mandate to rewrite working screens.

Use this when a feature changes what a person sees or does.Apply it to page layout, a new command, settings, empty states, dialog copy, a reusable control, and every custom visual. Pair it with the existing WinUI/XAML rules in AGENTS.md.

1. Wino’s north star

Focused correspondence

Email reading and writing stay central. Navigation and metadata support the message; they do not compete with it.

Dense, not crowded

Wino earns its density through alignment, hierarchy, progressive disclosure, and keyboard access—not tiny type or endless chrome.

Personal Windows workspace

Theme, wallpaper, Mica/Acrylic, and account context make the workspace feel owned while system conventions keep it instantly usable.

Design principles translated for Wino

EffortlessKeep high-frequency actions near the message, list, or event they affect. Preserve predictable keyboard and context-menu routes.
CalmUse whitespace, layered surfaces, and restrained color to create focus. Prefer one primary action and one visible hierarchy per region.
PersonalRespect the chosen app theme and account identity. Wino’s themed backgrounds are ambient, never a substitute for readable content contrast.
FamiliarUse native WinUI controls and Windows command vocabulary wherever they fit. Do not invent bespoke controls for familiar tasks.
Complete + coherentEvery feature works across light, dark, High Contrast, keyboard, mouse, touch, localization, narrow windows, and async states.

2. Product architecture and applicability

Wino is a mode-based productivity app—not a marketing site and not a card dashboard. Start with the feature’s home in this map.

Preserve Wino’s signature silhouette.The app shell may host Mail, Calendar, Contacts, and Settings; each mode can use the layout that serves its task. Do not force every new feature into cards, a top tab bar, or a new left navigation level.

3. Layout and density

Default structure

  • Use a stable structural pane and let the working content flex.
  • Use one clear page title or workspace anchor per content region.
  • Use 12, 16, 24, and 32 epx as the normal spacing rhythm; add space to show hierarchy, not decoration.
  • Allow mail content and schedules to use the window; avoid small, centered content islands.

Responsive rules

  • Large ≥1008 epx: side-by-side list/detail or calendar/details when valuable.
  • Medium 641–1007 epx: retain task hierarchy; collapse secondary panes or use compact navigation.
  • Small ≤640 epx: move from simultaneous panes to a deliberate drill-in flow; keep all critical commands reachable.
  • Breakpoints use the app window’s effective pixels, not monitor resolution.

Do: reserve dense layouts for repeated productivity data, such as messages and time grids. Avoid: shrinking controls, labels, or focus targets merely to fit another column.

4. Foundations: type, color, shape, iconography

Typography

Use the system type ramp and semantic WinUI text styles. Titles establish page hierarchy; body text optimizes scanning; metadata is quieter but remains readable.

  • Use sentence case and concise, task-led labels.
  • Never use placeholder text as the only field label.
  • Use tabular alignment or a fixed measure for dates, times, counts, and keyboard shortcuts.

Color

Semantic meaning wins over hue. Accent marks selection and primary action; success, caution, and danger describe an outcome—not a decoration.

Accent: selection, primary action, active focus
Success: completed / healthy state
Surface: content and layered containers
Stroke: separation and contour

Shape

Follow Windows geometry: 4 epx for controls and in-page backplates; 8 epx for dialogs, flyouts, and top-level containers. Do not round edges where panels meet flush.

Icons

Use familiar Windows symbols with accessible names. Pair unfamiliar icons with text; retain labels for consequential, destructive, and low-frequency actions. Do not use icon-only buttons without a tooltip and automation name.

5. Surfaces, elevation, and Wino personalization

Wino already ships a deliberate set of default, Acrylic, custom, and image-backed themes. Keep that personal touch, but put task content on reliable, readable surfaces.

LayerUse in WinoRule
Base layerWindow backdrop, app shell, navigation, ambient chosen themeMay expose Mica/Acrylic or the user’s selected background.
Content layerReading pane, editor, calendar canvas, settings contentUse a calm opaque or system-aware surface that protects content legibility.
Card / information areaBounded settings groups, explanatory status, optional detailsUse only when it segments a distinct task; not as default decoration.
Transient overlayFlyout, dialog, TeachingTip, menuUse built-in elevation; 8 epx corners for overlay surfaces.

Use existing semantic resources such as WinoApplicationBackgroundColor, ReadingPaneBackgroundColorBrush, MailListHeaderBackgroundColor, and platform ThemeResource brushes. Do not introduce hard-coded colors for new UI.

6. Navigation and information architecture

  • Keep global modes in the established shell. Add a mode only when it represents a persistent, distinct user job.
  • Keep folder/account navigation structural and stable. Selection belongs visibly to the current working context.
  • Use in-mode navigation for settings hierarchies and details; preserve Back behavior and state.
  • Use TabView for simultaneous documents/sessions, not as a generic page switcher. Use SelectorBar only for 2–3 peer modes.
  • For new deep flows, show a meaningful title and a deterministic way back. Do not rely on window close as navigation.

7. Commands, feedback, and recovery

Command placement

  • Core, frequent, object-specific action: on the canvas or command bar close to the object.
  • Secondary or rare action: overflow, menu, or context menu.
  • Text editing / selection action: CommandBarFlyout or contextual menu.
  • Primary irreversible action: explicit text label and confirmation.

Feedback hierarchy

  • Inline status for a field or localized operation.
  • InfoBar for actionable, non-blocking page status.
  • Flyout for compact contextual feedback or settings.
  • ContentDialog only for decisions that interrupt the task.
  • Use undo for recoverable mail actions; confirm only permanent or major consequences.

Use existing Wino command-bar and dialog styles. Destructive labels say the consequence: Delete permanently, not OK.

9. States and resilience are part of every page

A feature is unfinished until its normal and non-normal states are designed. Each collection, request, and editor must consider the following.

Loading

Explain what is loading and keep existing content stable when possible. Use skeletons only if they match the actual layout.

Empty

Say what the absence means and offer the next useful action: create, connect, adjust a filter, or refresh.

Error / offline

State the relevant cause in plain language and offer recovery. Keep offline and permission problems distinct from generic failure.

Selection

Support pointer and keyboard selection, a visible selected state, and sensible behavior when the selected item disappears.

Saving / sync

Show progress near the affected content. Prevent duplicate submission without silently discarding work.

Privacy / intelligence

Explain data scope, availability, and user control. Never imply an AI result is an authoritative action.

10. Accessibility is a release requirement

Accessibility is not a final polish pass. It protects the same Wino values as the rest of this guide: correspondence stays understandable, controllable, and personal for people using keyboard navigation, screen readers, magnification, text scaling, contrast themes, touch, or voice input.

Names and rolesEvery interactive or informative non-text element has a concise accessible name. Icon-only buttons also have a tooltip. Static content is TextBlock/RichTextBlock, not a disabled input or an artificial tab stop.Inspect the UI Automation tree and listen to the flow with Narrator.
KeyboardAll actions, including list selection, command overflow, dialogs, search, and recovery actions, work without a pointer. Do not use HighContrastAdjustment="None" unless the complete visual has system-aware replacements.Exercise the feature with a Windows Contrast theme—not merely Light and Dark.

Wino-specific accessibility decisions

  • Message lists: expose sender, subject, time, unread/flagged state, attachment state, and selection in a meaningful announcement; do not make color or bold weight the sole unread signal.
  • Reading and compose: preserve a predictable reading order from message header to body to attachments and actions. Give embedded WebView/editor content an equivalent accessible route and a clear loading state.
  • Calendar: expose date, time, title, calendar identity, and conflict/availability information in text. Keyboard users must be able to move, create, edit, and delete events without drag-only interaction.
  • Settings: use visible labels and plain-language helper/error text. Link descriptions to inputs; explain a setting’s impact before an irreversible or privacy-affecting change.
  • Intelligence: state availability, progress, origin, and limitations in text. Never encode local/cloud coverage, confidence, or failure by color or animation alone.
  • Personalized surfaces: a user-chosen backdrop is decorative. Reading surfaces, selected states, and focus cues remain legible independently of the backdrop.

Accessibility acceptance checklist

  1. Give every interactive element an accessible name; give every icon-only control both an accessible name and a tooltip.
  2. Perform the complete primary scenario using only the keyboard, including opening and dismissing overlays and returning focus.
  3. Use Narrator to check headings, lists, selected values, status changes, errors, and custom controls for clear announcements.
  4. Test Light, Dark, and a Windows Contrast theme; verify that no semantic information vanishes or relies only on color.
  5. Verify real text contrast at 4.5:1 or better and inspect personalized background combinations rather than assuming a token is sufficient.
  6. Check enlarged text, display scale, and Magnifier for clipping, overlap, lost labels, and unreachable commands.
  7. Run the XAML automation-ID audit and exercise the behavior through the installed Debug app with WinApp CLI after Visual Studio deploys it.

11. Implementation decisions for WinUI XAML

Design tokens are existing semantic resources first.Before adding a style, search the shared resources and control library. Extend the design system at the narrowest reusable level; avoid page-local copies of standard control templates.
  • Use built-in WinUI controls and styles unless Wino has a reusable control that owns the interaction.
  • Use {ThemeResource} for UI-facing colors and brushes; use {StaticResource} inside a theme dictionary except for system resources that must update.
  • Base custom styles on the platform default. Do not re-template standard controls just to change one brush, margin, or corner.
  • For x:Bind, explicitly select Mode=OneWay for changing view-model values; use UpdateSourceTrigger=PropertyChanged for text that must update while typing.
  • Keep XAML visual composition in XAML, use semantic resource names, and preserve the repository’s established Wino styles: WinoDialogStyle, PageRootBorderStyle, InformationAreaGridStyle, and TransparentActionButtonStyle.

12. New-feature design workflow

  1. Name the task. Write the user’s primary task, supporting tasks, content density, and feature home (Mail, Calendar, Contacts, Settings, or Intelligence).
  2. Choose the silhouette. Decide whether it belongs in the existing shell, a list-detail workspace, a focused editor, or a settings flow. Do not start with a control.
  3. Map the states. Specify loading, empty, error/offline, selection, save/sync, and destructive/recovery behavior.
  4. Choose native patterns. Map every interaction to a WinUI control and existing Wino style; explain any custom control exception.
  5. Write the responsive plan. Describe large, medium, and small-window behavior, including which content moves, collapses, or becomes a drill-in.
  6. Specify accessibility. Identify keyboard flow, focus return, automation IDs, names, and High Contrast behavior.
  7. Build and verify. Review theme states and the XAML automation-ID audit; deploy via Visual Studio and exercise the changed flow against the registered Debug app.
