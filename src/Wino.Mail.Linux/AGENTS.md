# Wino.Mail.Linux

The Linux app for issue #1216: GTK 4 and libadwaita through Gir.Core, with WebKitGTK 6.0 for the reader and the composer, written in C# over the shared services and ViewModels. It runs on CoreCLR. It targets GNOME on Wayland (Fedora and Ubuntu) and adapts to tiling compositors and Omarchy through the desktop profile ([Linux design decisions](../../docs/linux-design-decisions.md)). It has Mail, Calendar, Contacts, To Do and Settings with account setup and sign-in; the features it skips are in the [port plan](../../docs/linux-port-plan.md#status). It is released as a beta `.deb`, an Arch package (also for Omarchy and the AUR `wino-mail-bin`) and a Fedora RPM ([Linux release guide](../../docs/releases-linux.md)); a packaged copy has a `distribution` file beside the executable, which turns on the update check (`Infrastructure/Updates`), "(Beta)" in About and telemetry. Its `package=` line (`deb`, `arch`, `rpm`) picks the feed entry through `Infrastructure/Updates/LinuxPackageKind`; an Arch copy's Update only opens the download page. This file is binding for `src/Wino.Mail.Linux`; platform services are in [Wino.Platform.Linux](../Wino.Platform.Linux/AGENTS.md).

## Hard stops

- No Uno, Avalonia or MAUI. The UI is GTK widgets built in code.
- No test projects, and no reference to `Wino.Hosting`: no app may reference it.
- Shared projects get no Linux-only change. They must still build for Windows.
- Never fix a bug in shared code (`Wino.Core*`, `Wino.Services`, `Wino.Mail.ViewModels`, providers, `controls/*.Core`, other heads) from Linux work. Record it as a handoff with its cause and fix idea in the [port plan](../../docs/linux-port-plan.md#open-handoffs-to-shared-code); a mitigation is allowed only when it touches Linux projects alone (`Infrastructure/DatabaseJournalRecovery` is the example). The only shared touches are additive English strings and Linux build entries.
- Outlook signs in through MSAL with the system browser and `http://localhost`, with the Entra app of `IAuthenticatorConfig`; the token cache is a secure item (`msal-cache`). Gmail mailboxes sign in through the shared loopback receiver (`WinoGmailCodeReceiver`, registered by `AddGmailProvider`) with the client that `IAuthenticatorConfig` supplies, the same flow as Android's fallback (owner decision for issue #1216). Never name a Google client id in a Linux project, never change that client, and never use it for Wino Account sign-in; the rules are in the root guidance.
- The application id `app.winomail.Mail` (`Program.ApplicationId`) is the GApplication id, the name of the `.desktop` file and the application attribute of the keyring item. Never change it.
- `--lab-lease` works in Debug builds only (`LabAccountBootstrap`). Never log the lab password.
- This project is plain `net10.0`, so the shared Release gate applies: Native AOT, trimming and single-file analyzers with warnings as errors. Keep it clean; do not exempt the project.

## How a view consumes a ViewModel

A view is a plain class that builds its widgets in the constructor and exposes `Root`. There is no XML, no Blueprint and no GObject subclass except `ManagedItem`, the list item type. A layout that needs managed measure and allocate never uses Gir.Core's `Gtk.CustomLayout.New`: its delegates are collected and the app crashes (JIT FailFast, AOT SIGSEGV). Use `Gtk.Fixed` or a box, or call `gtk_custom_layout_new` with `[UnmanagedCallersOnly]` function pointers and wrap it with `Gtk.CustomLayout.NewFromPointer`.

- A routed view derives from `WinoView<TViewModel>` (`Infrastructure/WinoView.cs`) and is created with `PageScopes.Create<T>(services)`: the view and its transient ViewModel live in a DI scope of their own, which `ReleaseAsync` disposes. Views are not registered in the container; a view needs a public constructor whose parameters are container services, the ViewModel first. The view binds through `Bind` (a `GtkBinder` from `Wino.Presentation.Linux`) and `Bindings`, subscribes to messages with `Subscribe`, and overrides `InitializeAsync` and `DeactivateAsync`. `MailListView` is the example.
- `GtkNavigationService` is the host of the shared `NavigationCoordinator`. Routes are in `Infrastructure/LinuxPageRegistry.<Area>.cs` (`Register<TView>(page, host)`), head services in `Infrastructure/LinuxViewModelRegistration.<Area>.cs`; a new page edits neither `LinuxComposition.cs` nor `GtkNavigationService.cs`. A page without a route is refused. The reading pane (`ReadingPaneHost`) belongs to whoever calls `AttachRenderingHost`, today the shell; it keeps a page only when the view implements `IRenavigableView` (the reader) or is the idle view, and releases any other page when the next one shows.
- `ShellLayout` (`Views/Shell`) owns the panes and their widths; `ShellMetrics` holds every size. The sidebar docks from 860 px and is an overlay below; the list and the reader stack when the content area is narrower than the list and reader minimums together. The sidebar width and the window placement are kept by `WindowStateStore`, the list width by `IStatePersistanceService.MailListPaneLength`.
- A content page shown beside the reading pane implements `IUsesReadingPane`; any other page gets the whole content area and may split it with `ListDetailSplit`. Pages in the content area have no header bar with window buttons: the shell's one header spans the content area.
- The shell's one header is `ShellHeaderBar` (`Views/Shell`). The content view may implement `IShellSearchTarget` (`Infrastructure/ShellContracts.cs`) to receive the header search entry. Header buttons for Daily briefing, What's New and Wino Account appear when their presenter is registered. Application actions are in `Infrastructure/AppActions.cs`; add an accelerator there, not in a view.
- The sidebar is `ShellSidebarView`, a `Gtk.ListView` over `ShellMenuRowPresentation.Flatten`/`Describe` drawn by `WinoShellRow`. A row is invoked by a selection change (pointer, accessibility clients) or by Enter; the arrow keys only move the focus, Left and Right collapse and expand. Other packages extend it through `CellSetup`/`CellTeardown`, `RowsChanged`, `AddRowProvider` and partial files of the class.
- Sidebar menus are data (`ShellSidebarContextMenus.Build`); other areas add entries with `AddExtension`, once at startup. `ShellSidebarMenuPresenter` shows them through `ContextMenu`; a menu action runs after its popover closed.
- The mail list sends `ActiveMailFolderChangedEvent` after `OnNavigatedTo` and awaits `WaitForCurrentFolderInitializationAsync`. Without it the shell never shows its menu.
- Rows come from shared presentation code: `ShellMenuRowPresentation` for the sidebar, `MailListProjection`, `MailRowPresentation` and `MailListSelectionSnapshotBuilder` for the list. A cell only renders.
- Mail rows: `MailRowMapper` maps, `MailRowCell` binds, `WinoMailRow` renders.
- New lists use `ObservableListModel<T>`, `WinoCellFactory` and `ListSections` from `Wino.Presentation.Linux.Lists`. A page disposes its factories, sections and model when it is released (`Bindings.Own`).
- The mail list holds `MailListEntry` items (rows only); date groups are GTK sections, and store order equals screen order, so a position indexes the view's own row array (`EntryAt`, `PositionOf`). Projection changes apply at most every 120 ms as the smallest splices. A package extends `MailListView` through a partial file and the hooks (`MailListView.cs`, `MailListView.Features.cs`), never by editing `MailListView.cs`; every GTK handler of the view reaches it through `_self`.
- A mail list feature lives in `Views/Mail/MailListView.<Feature>.cs` and hooks in through `MailListView.Features.cs`. A command on a row takes its targets from `MailListTargets.For`. The row context menu is data (`MailContextMenuModel`) shown through `ContextMenu.AttachRequest` and `ContextMenu.Show`, because it loads categories and folders before it opens.
- The mail list action bar is `MailListView.ActionBar.cs` over `ViewModel.ActionItems`, hosted in `MailListHeader.ActionBarSlot` and reusing `MailReaderCommandBar`.
- The mail list header and the bars around the list are `MailListHeader` and `MailListBars`, wired in `MailListView.Header.cs`. Undo and the page's update message are floating `WinoInfoBar` cards over the bottom of the list; window-level messages stay with `InfoBarHost`.
- Contacts mode is `Views/Contacts/ContactsPageView` over `ContactsPageViewModel`, which outlives its page (it publishes the sidebar menu): every subscription on it, its collections and its items is owned by `Bindings`. A page with a fixed end pane (contact detail, task drawer) uses `Views/Common/EndPaneLayout` on the page's own width; a blocked mode shows `Views/Common/ModeReadinessPanel`.
- To Do mode is `Views/ToDo/ToDoPageView` over `ToDoPageViewModel`, which outlives its page. The page is a frame of hosts (header, filter row, list, quick add, drawer) in an `EndPaneLayout` that swaps below 728 px; the list, the filters and the drawer are partial files that implement its `partial void Build…/Bind…` hooks. Sidebar entries for task lists and groups are `ToDoSidebarMenus`.
- Forms (the contact editor) are libadwaita preference groups bound with `Bind.BindText`; a field over a plain entity (an e-mail address, a phone) is written through `GtkSignals.OnChanged` in the row's own scope and calls the ViewModel's `MarkDirty`, so loading never marks the form dirty.
- The composer is `Views/Mail/Compose/ComposeView` in the reading pane over one `WebKitGtkHtmlMailEditorSession`. A composer feature lives in `ComposeView.<Feature>.cs` and implements its `Initialize*`/`Deactivate*` partial-method pair or fills a slot (`CommandSlot`, `ToolbarSlot`, `AttachmentSlot`, `PageOverlay`); only an edit autosaves, never the echo of rendering a draft. `ComposeDetachedDraftRouter` shows a draft the list does not list and returns the pane to idle after send or discard; a listed draft is selected through `SelectMailItemContainerEvent` (`MailListView.DraftSelection.cs`).
- The mail list implements `IShellSearchTarget` in `Views/Mail/MailListView.Search.cs`; the scope bar is `Wino.Mail.Controls.Linux.MailList.WinoSearchScopeBar`. A search always goes through `MailListPageViewModel.SearchAsync` with the scope bar's reach. An emptied header entry is a text change (a filter-only search stays); Escape and Done clear.
- The mail list's selection is read from the view's own row array, never item by item from GTK; select all is one range bitset. A list page covers the reading pane through `GtkNavigationService.SetReadingPaneCover` (`IRenderingFrameHost.SetCover`); the multi-selection summary is the only user.

```csharp
public MailListView(MailListPageViewModel viewModel, WinoViewServices services, LinuxSenderPictureProvider pictures, GtkNavigationService navigation,
    IFolderService folders, IKeyboardShortcutService shortcuts)
    : base(viewModel, services)
{
    ViewModel.MailCollection.CoreDispatcher = Dispatcher;
    Projection = new MailListProjection(ViewModel.MailCollection.Items, ViewModel.MailListOptions ?? new MailListProjectionOptions());
    Bind.Bind(nameof(MailListPageViewModel.MailListOptions), static vm => vm.MailListOptions, options => Projection.SetOptions(options ?? new MailListProjectionOptions()));
}
```

## Always

- Every Wino concept glyph is a `WinoIcon` or `WinoIcons.Label`/`Button` from `Wino.Presentation.Linux`. Adwaita icon names only for GNOME chrome (back, close, menu, window controls, expanders) and for widgets that take an icon name only.
- Every interactive widget has an accessible name (`WinoA11y.Label`, or `LabelWithTooltip` for icon-only buttons), and a widget hidden until hover is also hidden from accessibility. Navigation rows react to selection, because AT-SPI cannot activate a `Gtk.ListBox` row; a key, drag or gesture that AT-SPI cannot produce gets a Debug action in the feature's `Infrastructure/Diagnostics/<Feature>DebugActions.cs` (inside `#if DEBUG`) that runs the same code path. Never take pictures through the Screenshot portal.
- Touch widgets on the GTK main thread only. ViewModel notifications can arrive on other threads; go through `IDispatcher` or `GLib.Functions.IdleAdd`.
- Connect GTK signals only through `GtkSignals` (`Connect`, `OnClicked`, `OnNotify`, ...) or `GtkBinder`, and own the returned subscription in `Bindings`. Gir.Core 0.8.1 keeps a handler in the object's closure table after `-=`, so a raw `+=` whose handler captures the view keeps it alive with its widgets; the helpers reach the handler through a box that disposing empties. `MailListView` is the example. Raw `+=` is fine only for handlers that live as long as the app.
- Initialize a Gir.Core module before its first use when nothing else does: `WebKit.Module.Initialize()` runs in the reader session. Without it the native library is not found.
- Take user-visible text from `Translator`. A Linux-only string is added to `resources.json` with the `Linux_` prefix, and its builds on the other machines are reported as pending.
- Register a new head service in its area's `Infrastructure/LinuxViewModelRegistration.<Area>.cs` hook, never in [LinuxComposition.cs](LinuxComposition.cs); platform services go to `Wino.Platform.Linux`.
- A folder is picked with `Views/Dialogs/FolderPicker` (the move dialog in `GtkDialogService.Folders.cs`; under a Move button `Views/Mail/MoveFolderPopover.ShowForAsync`). Do not build another folder list.
- Pickers use `Views/Dialogs/ListPickerDialog` (`GtkDialogService.ListPickers.cs`); the account reorder, alias and category dialogs are `Views/Dialogs/AccountReorderDialog`, `CreateAliasDialog` and `EditMailCategoryDialog` (`GtkDialogService.Accounts.cs`).
- A dialog without a screen stays in `GtkDialogService.Dismissed.cs`. Its package moves it into its own `GtkDialogService.<Group>.cs` and builds it on `AlertAsync(AlertRequest)` (`Views/Dialogs/AlertPresenter`), `FormDialog` or `FilePickers`, presented through `PresentAsync(owner => ..., dismissed)` so it runs on the main thread and hangs from the active window. Files and folders are picked only through `FilePickers`.
- Configurable shortcuts are routed by `ShortcutRouter` (one capture-phase key controller per window, owned for the main window by `ShortcutHost`). A page handles them in its ViewModel's `KeyboardShortcutHook`; views add no key handler for a configurable action. A secondary window creates its own router with `IsPopOut`.
- Every fixed key is a row of `Infrastructure/LinuxKeymap.cs` and an application action; registration, the router, the overview (`ShortcutsOverview`), tooltips, menu hints and the recorder's conflict check read that table, so add a key there and nowhere else. `Global` keys are accelerators and act only while the main window is active (`AppActions`), except Preferences, Quit and close-window. `Context` keys get no accelerator, because accelerators fire inside dialogs, popovers and entries: the router matches them after the configurable shortcuts and runs `ShortcutRouterContext.RunFixed`, which returns false to let the key pass on (Escape in the list clears its selection). Single keys (j, k, r, e, ...) act only in Mail, with list or reader focus, while `SingleKeyShortcuts` is on (head-local key `LinuxSingleKeyShortcuts`; without a choice it follows the Tiling window style). The reader's web view carries `ShortcutRouter.ReadOnlyWebClass`, so it counts as text input only for copy gestures.
- Pane focus goes through `ShellView.Focus.cs`: a content page or reading-pane view implements `IPaneFocus` (where focus lands), `IDetailPane` (a detail pane of its own and Enter into it), `IItemNavigation` (Alt+Down and Alt+Up) and `IKeyActionTarget` (its own fixed keys) from `ShellContracts.cs`. Do not call `SetFocus(null)`: the shell puts a lost focus back into the pane that had it.
- A window besides the main window is a `SecondaryWindow` (`Views/SecondaryWindow.cs`) registered with `WindowManager` under a key (`mail:<id>`, `composer:<draftId>`, `event:<id>`, `whatsnew`, `onboarding`); its view is released in `Closing`, and stop closes every window first. The Settings window keeps its own presenter.
- A `wino://auth-complete` address is handed to `LinuxExternalAuthCallbacks` in `LinuxApplication` before activation routing, and its query is never logged. The browser sign-in waiting dialog is `ExternalBrowserAuthPresenter` (`Infrastructure`).
- Purchases use the Wino Account channel only (`Purchases: true`, no store): `WinoBillingService.OpenCheckoutAsync` gets the checkout address from the API, so no checkout address lives in the client, and the shared `ActivationRouter` routes `wino://billing/success` to Settings › Wino Account.
- Wino Intelligence settings are `Views/Settings/Intelligence` (home, mail classification, per-account management, coverage editor). The Settings window builds a new page on Back, so the coverage editor hands its result to the management page through `IIntelligenceCoverageHandoff`, as on macOS. The consent dialog loads the policy in an ephemeral WebKit session without JavaScript.
- The Daily briefing panel (`Views/Extras/DailyBriefingPanel`) belongs to `DailyBriefingPresenter` and outlives the shell; `ShellLayout` hosts it in its trailing pane (`SetTrailingPanel`), docked only from `ShellMetrics.TrailingPanelDockedMinimumShellWidth`, floating over the content below it.
- The desktop profile is `LinuxDesktopProfile` (`Infrastructure`) over `Wino.Platform.Linux.Desktop`: the window style (Automatic, Standard, Tiling) and Follow the Omarchy theme. Window buttons are set for every header bar at once by `WindowChrome` (`gtk-decoration-layout`); no view adds or hides window buttons. The flat tiling look and the Omarchy palette are emitted by `ThemeCss` through `GtkThemeService.Desktop.cs`, under the palette rule of the design decisions; `OmarchyThemeWatcher` follows theme switches live. Content must survive a 460 × 490 tile: a footer that does not fit below 620 sp gets a breakpoint (`OnboardingUi.NarrowBin`), and `debug-desktop-report` must show no OVERFLOW.
- Window-level messages go through `IMailDialogService.InfoBarMessage` (or the `InfoBarMessageRequested` message) to the window's `InfoBarHost`; a view never creates a host.

## Check your change

- **On a Linux host:** the Debug build, the Release build (the gate), then checks in a GNOME Wayland session with the lab account of a persistent development profile: Debug actions, AT-SPI, screenshots and `debug-live-objects` for leaks. Real keys, pointer, touch, portal pickers and OAuth sign-ins are owner checks. Commands, the keyring a development session needs and the profile workflow are in the Linux guide.
- **On a Windows or Mac machine:** build the shared projects you touched and report "Linux Debug and Release builds and manual checks pending" with the list of changed files.

A build does not prove UI behavior.

## Performance

- Coalesce rebuilds: a list rebuilds once per main-loop turn (a `MainLoop.Coalescer`) or, for the mail list, once per 120 ms throttle window, not once per notification. In the sidebar a menu item's property change repaints one row; only a structure change re-flattens, once per main-loop turn.
- Appending a loaded page must stay an append to the list model, so the scroll position is kept.
- The reader reuses one web view and one ViewModel for every message.

## Reader

- The reader is `MailReaderView` (`Views/Mail`) plus one `MailReaderView.<Part>.cs` per feature, wired through the `partial void Build…/Initialize…` hooks and the `WhenRenavigating`/`WhenRendering`/`WhenWidthChanged` lists; a part never edits `MailReaderView.cs`.
- The reader theme comes from the ViewModel (`IsDarkWebviewRenderer`); the style manager only reports the app theme through `ApplyApplicationTheme`.
- The reader's width state (Wide, Narrow, Compact) comes from its own probe, never from a breakpoint, and its minimum width stays at or under `ShellMetrics.ReaderMinimumWidth`.
- The reader's command bar (`MailReaderCommandBar`) takes its width from the reader's probe; commands that do not fit move into More. Its commands come from `MailReaderCommandLayout` over the ViewModel's menu (Settings > Reader actions), with Move next to Delete through `MoveFolderPopover`.
- Attachments are `AttachmentStrip` tiles with system file-type icons (`Infrastructure/AttachmentFileIcons`); in Debug builds `debug-next-folder` answers the next folder picker.
- `IRenderingFrameHost.SetCover` covers the pane with a list page's widget while the reader stays alive underneath.
- Sender pictures come from `LinuxSenderPictureProvider`; never decode an image in a cell bind.
- The privacy button, its popover (`ReaderPrivacyPopover`), the three remote-content bars and the hovered link's address (`ReaderLinkTargetBar`) live in `MailReaderView.Privacy.cs`; the bars offer Load once only, every other privacy action is an item of `ViewModel.PrivacyMenuItems`.
- Print and PDF export go through `LinuxMailPrintPresenter`, which each reader sets as `ViewModel.PrintPresenter` over its own web view; the message source is `Views/Dialogs/MessageSourceDialog`.
- The invitation card is `MailInvitationCard`, bound to `ViewModel.Invitation` only; it holds no reader knowledge, so other surfaces can reuse it.
- Pop out moves the live reader (view, ViewModel, web session) out of the pane (`IRenderingFrameHost.Detach`) into a `SecondaryWindow` under the key `mail:<file id>`; an opened `.eml` file is the same reader with `HostKind.File` in a `file:<path>` window (`EmlReaderWindow`). `ReaderWindowRegistry` names the keys and keeps the composer pop-out a popped-out reader asked for; `WindowManager` closes every reader window on stop.
