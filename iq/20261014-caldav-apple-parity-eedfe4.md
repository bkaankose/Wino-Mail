## Purpose
Bring Mail-Cal's CalDAV calendar synchronization closer to Apple Calendar in the shared backend only: incremental sync, a per-server capability model that the shared ViewModels adopt, DNS SRV discovery, attachments where the server supports them, and the small items (Prefer header, default alarms, quota). Out of scope by user decision (2026-10-14): push, sharing and the notification collection, the scheduling inbox and outbox (and therefore free/busy, which needs the outbox), and VTODO task lists. No Windows or macOS UI head work, no app launch. Research is in `20261014-caldav-apple-parity-eedfe4/research.md`.

## Agreement
Plan: Approved
Approval: 2026-10-14, user answered "Approve (Recommended)" to the plan question after the full plan was printed with their corrections (scope cuts, shared-layer handling of denied actions).
- Plan: T1 first (foundation, incremental sync, capability model), then T2–T4 in parallel on non-overlapping files, then T5 integration and verification.
- Decisions/constraints:
  - No database schema change of any kind: no new table, column, index, schema version, or `__MigrationMetadata` entry. New CalDAV state is a JSON cache file beside the ICS store (`CalendarIcs/<account>/caldav-state.json`). If an item needs a schema change, it records the need and skips that part.
  - Existing users change no settings: new behavior switches on from server capabilities when the account already uses `ImapCalendarSupportMode.CalDav`. `AccountCalendar.SynchronizationDeltaToken` keeps its `win=YYYYMMDD|<token>` format.
  - Out of scope (user, 2026-10-14): push, sharing/delegation, notification collection, scheduling inbox/outbox, free/busy, VTODO.
  - Capabilities are the product: a provider-neutral `CalendarCapabilities` model (per account and per calendar) served by a shared `ICalendarCapabilityService`; CalDAV fills it from the DAV header, supported reports, component sets, quota and limits; Outlook, Gmail and local fill static sets. Shared ViewModels replace hard-coded provider checks (for example `CanAddAttachments => !IsSelectedCalendarCalDav`) with capability reads. Denied actions are handled in the shared ViewModels and services (the action is refused there with a translated message through the existing dialog/notification services), not by reshaping native UI; heads stay thin. XAML and AppKit changes are limited to whatever the heads need to surface an already-exposed ViewModel property and are a handoff.
  - Architecture: CalDAV sync moves out of `ImapSynchronizer` into `src/MailCal.Core/Synchronizers/CalDav/` (mirrors the CardDAV engine); `CalDavClient` and `ICalDavClient` become `partial` with one file per feature so parallel items never edit the same file. `src/MailCal.Calendar.ViewModels` is legacy and is not edited.
  - Subagents: Opus 5.5 (`model: opus`), effort `high`, one per item; reports under `iq/20261014-caldav-apple-parity-eedfe4/`. Credentials are passed in briefs and a scratchpad file only, never written to the repository or this record.
  - No commit, no push, no app launch. Windows Debug/Release gates and Mac builds are a handoff.
