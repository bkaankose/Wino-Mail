## 1. P1 — crashes to fix (Windows head / editor controls)

### 1.1 Settings NavigationView `invalid vector subscript` — WINOMAIL-2Q5 (fatal 521 ev / 32 users), 2Y5, 2ZP, 2Z4, 33T, probably 2W6
Evidence: `ArgumentOutOfRangeException ... invalid vector subscript`, no managed frames on the fatal ones; 7 of 10 sampled events have `app_mode=settings`. WINOMAIL-33T carries the frames: `ABI.Microsoft.UI.Xaml.Controls.INavigationViewMethods.set_SelectedItem` ← `ObservableObject.SetProperty` ← `SettingsMenuProvider.SetSelectedRootPage` (`src/MailCal.Core.ViewModels/SettingsMenuProvider.cs:227`) ← `WeakReferenceMessenger.Send(ActiveSettingsPageChanged)` ← `SettingsPage.RefreshCurrentPageStateAsync` (`src/MailCal.Mail.WinUI/Views/SettingsPage.xaml.cs:513`).
Mechanism: `MailCalAppShell.xaml:85` binds `SelectedItem="{x:Bind ViewModel.SelectedMenuItem, Mode=TwoWay}"`. `SetSelectedRootPage` selects a `SettingsShellPageMenuItem` that is a child of a `SettingsShellGroupMenuItem`; `ExpandGroupContaining` flips `IsExpanded` on the model, but the `NavigationViewItem.IsExpanded` TwoWay x:Bind (`Styles/ShellMenu/ShellMenuTemplates.xaml`) and the child container realization are not synchronous, so NavigationView indexes a child that is not yet in its realized vector and throws. Also happens on `RebuildMenuItems` (items cleared and re-added while a selection exists) during mode activation/language change.
Fix direction: 
- In `MailCalAppShell` code-behind, stop pushing selection through the TwoWay x:Bind for hierarchical items. Subscribe to `SelectedMenuItem` changes and set `navigationView.SelectedItem` only after the owning group's container is expanded (`navigationView.ContainerFromMenuItem(group) is NavigationViewItem { IsExpanded: true }`), deferring to the next dispatcher tick / `UpdateLayout()` otherwise; wrap the set in `try/catch (ArgumentOutOfRangeException | COMException)` with a retry once and a log.
- In `SettingsMenuProvider.RebuildMenuItems`, clear `SelectedMenuItem` before `Items.Clear()` and restore it after items exist (it currently keeps the stale selection while the vector is empty).
- Check `MenuItemCollection` for the same pattern on the Mail shell (2W6 `selection has changed since SelectedIndices property was read` is a ListView multi-select race: `MailListPage` reading `SelectedItems/SelectedRanges` while the collection mutates — guard with dispatcher ordering, see commit `35038a43 Guaranteed dispatcher calls for listview`).
Verify (Release package): open Settings from the footer mode switcher with every group collapsed; deep-link via settings search into a page inside a collapsed group; open Settings → Mail-Cal account → back; switch Mail ⇄ Settings ⇄ Calendar ⇄ Tasks 20 times; change language in Settings (triggers rebuild). No crash, correct item highlighted.

### 1.3 `This element is already associated with a XamlRoot` — WINOMAIL-2DD (fatal 48/8), 33S
No managed frames; 9 of 10 sampled events in `app_mode=settings`. Candidates:
- `src/MailCal.Mail.WinUI/Views/Settings/MailCalIntelligencePage.xaml.cs:32,37`: `ConsentPolicyDialog` / `ConsentRevokeDialog` are XAML-declared dialogs whose `XamlRoot` is reassigned on each show. If the page instance is cached (navigation cache) and shown in a different window (settings in its own window vs main window), the second assignment throws exactly this. Set `XamlRoot` only when `dialog.XamlRoot is null`, or create the dialogs per show.
- `src/MailCal.Mail.WinUI/Services/DialogServiceBase.cs:41,184,257`: `GetXamlRoot()` returns `MailCalApplication.MainWindow.Content.XamlRoot`. Audit the cached dialog instances in `DialogServiceBase` and `src/MailCal.Mail.WinUI/Services/*DialogService*.cs`; resolve the XamlRoot from the window that owns the request (the `IMailCalWindowManager` current/active window), and never reuse a `ContentDialog` instance across windows.

Verify: open Settings in a separate window and in the main window; on AI features toggle consent on/off twice; trigger a dialog-service dialog (e.g. account removal confirmation, special folder configuration) from both windows.

### 1.9 Database initialization races — WINOMAIL-34M, 34K, 33P (fatal, `Cannot create commands from unopened database`), 330 (fatal NRE in `sqlite3_changes`), 34C (NRE in `sqlite3_prepare_v2`)
Frames: `DatabaseService.CreateTablesAsync:207/208` (`EnsureIndexesAsync`, `EnsureLocalAddressBooksAsync`) ← `DatabaseService.InitializeAsync:100` ← runtime step 2 ← `App.EnsureCoreActivationInfrastructureAsync:863` ← `OnLaunched:921`. The connection is closed/replaced while table creation runs. `DatabaseService.InitializeAsync` (`src/MailCal.Services/DatabaseService.cs:59`) has no concurrency guard: `_isInitialized` is set only at the end, and `Connection = new SQLiteAsyncConnection(...)` is assigned at the start, so two overlapping callers (step 2 runs `database().InitializeAsync()` in a `Task.WhenAll` alongside `synchronizationInitializer()`/`intelligenceStore()`, and migration/activation paths call it too) replace the live connection mid-flight; `EnsureCompleted210DatabaseAsync:118` also closes it. Fix: make `InitializeAsync` single-flight (`Lazy<Task>`/`SemaphoreSlim`), never reassign `Connection` once created, and if validation fails close only the local handle. 34C: `ToDoPageViewModel.ReloadLoopAsync:1158` keeps querying after the connection is closed on shutdown → stop the loop on runtime stopping and catch `SQLiteException`/`NullReferenceException` from the native layer as "database closed".
Verify: cold launch 10×; launch via toast while the app is closing; launch, immediately close while the ToDo page is open.

### 1.10 Missing theme resources — WINOMAIL-332 (fatal 4/3), 34B (fatal 3/1)
